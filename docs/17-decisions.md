# 17 · Decisions

A log of decisions with reasons. Change a decision by adding a new entry that supersedes it.

| # | Date | Decision | Why |
|---|---|---|---|
| D-01 | 2026-10-12 | Build a **generic** orchestrator; Mohalla Mitra is the first use case, not the definition | The pattern (stages, generate→check→fix, shared assets, learned fixes) recurs across many domains |
| D-02 | 2026-10-12 | **One engine, step kinds as equals**: workflow nodes, agents, tools, UI actions; any can contain or call the others | Agents and humans are both "steps that take a long time"; one primitive (complete / spawn / suspend) keeps the engine small |
| D-03 | 2026-10-12 | **Durable execution via an event log**; humans and model jobs use the same suspend/resume tickets | Resumability, lineage, audit, KB mining; manual mode for free |
| D-04 | 2026-10-13 | **Candidates are automatic (config); branches are explicit (user says "branch off")**, named and saved | Images benefit from best-of-N every time; story direction changes are deliberate and need their own history |
| D-05 | 2026-10-13 | When a branched upstream is locked over the original, downstream work is **marked stale and parked** (not kept as an alternate cut). Only work whose inputs changed goes stale; re-locking restores it | Keeps one active cut; nothing is lost |
| D-06 | 2026-10-13 | Primary authors are **non-technical creators** | Drives recipe-style builder, generated screens, plain language, templates first |
| D-07 | 2026-10-13 | **Creators define their own levels**; project/episode is only the starting template | Different domains have different hierarchies (channel → series → episode → shot) |

| D-26 | 2026-10-15 | **The engine owns the agent loop**: an agent executor takes one turn per call; every turn and tool result is an event; asking a human is a built-in `ask_human` tool | Crash-resume mid-agent with no repeated calls; per-turn budgets; long-running agents use the same suspend/resume path as everything else |
| D-27 | 2026-10-15 | Agent `max_turns` is **configurable with no fixed ceiling** (default 8); agent nodes take an optional **`budget: { usd }`**; the validator warns above 50 turns without a budget. Resolves Q-14, Q-15 | Long-running agents are a real use; the budget is the real limit on spend, turns are a weak proxy |
| D-28 | 2026-10-15 | **In automatic mode, locked nodes don't ask first.** Supersedes the last sentence of D-08. Ask mode stays the default. A change to a lock in auto mode is recorded as an auto-approved proposal, notified in the inbox, and revertible to the previous lock. Resolves Q-01 | Auto mode should mean automatic; safety comes from history and one-step revert, not from a prompt |
| D-29 | 2026-10-15 | **A lock carries an optional "why"**: the creator's own lock note, verbatim (never an AI summary; no note → nothing). It is a field of the lock (`<node>.why`), part of downstream cache keys. Agent and LLM steps receive it by default; media models only via explicit `uses: [<node>.why]`. Resolves Q-02 | Carries intent forward without leaking chat (D-11); deterministic and replayable; media prompts stay clean |
| D-30 | 2026-10-15 | **Two version operations: `replay_change` and `adopt`. Build `replay_change` first.** `replay_change` re-applies a recorded instruction to another version, branch or item (one parent). `adopt` merges two versions into a new one (two parents); for media it is a model call checked like any candidate. Both only create candidates; neither touches sources or moves locks. Resolves Q-03 | Replay is simpler and is what Part 3 needs (same fix across shots); merge for media is a guess and must earn its lock |
| D-31 | 2026-10-15 | **v0.1 providers: Anthropic** for reasoning and navigation (agents, checkers, planning, builder assistant), **Replicate** for real media generation, **Fake** as a first-class provider for quick testing and the no-keys demo. Others use manual mode. Resolves Q-04 | One clear job each; Replicate already reaches hundreds of media models; Fake makes tests free and clone-to-running possible without keys |
| D-32 | 2026-10-15 | **Autonomous agents write their own tools (sandboxed) and choose, discover and switch providers** without asking in auto mode, within budget, model versions pinned. **The engine holds the keys** (secrets broker); agent code never sees them. **Promoting** sandboxed code to a trusted tool needs human review. Unreviewed, unsandboxed AI code: never. Sandboxed agent tools move from v0.4 to **v0.2** (Deno / Docker). v0.1: creators write tools. Resolves Q-05 | Autonomy is bounded by blast radius, not approval clicks: sandbox + budget + no key access make the worst case a failed step; only leaving the sandbox is irreversible |
| D-33 | 2026-10-15 | **Recipe files are the source of truth.** A recipe folder (YAML/JSON, in git) is the canonical definition; publishing snapshots it into an immutable, hashed release stored in the DB for runs to pin (refines D-14). The builder reads and writes the files via graph operations, keeping comments and order. No separate export. Run data (locks, runs, assets, media) stays out of git. Resolves Q-06 | One source of truth, no drift between DB and git; forks are `git clone`; recipe changes get PR review |
| D-34 | 2026-10-15 | **Stream by default, barriers opt-in.** Between maps linked by the same item key, an item moves on as soon as its own output is locked. Joins over whole maps wait for all. A set-level review is `wait: all` plus a screen on the set. Resolves Q-07 | Shortest wall-clock time; safe because only locked outputs move (rule 3); joins and set reviews keep their barrier |
| D-35 | 2026-10-15 | **Run-time changes by humans.** Item changes (split, add, merge, remove a shot) are edits to a locked list: the map re-materializes, unchanged keys keep their work, removed keys are parked, new keys start (v0.1). Structural changes to one run go through an episode override → release → run upgrade (v0.2). The live graph is never edited in place. Resolves Q-08 | Stable keys and stale tracking already handle item changes for free; in-place graph edits would break replay |
| D-36 | 2026-10-15 | **Conditions UX: sentences with pickers, plus free typing the assistant converts.** Converted conditions are shown back as pickers for the creator to confirm and saved as the plain condition language; the assistant runs only at authoring time. Resolves Q-09 | Non-technical creators get natural phrasing; conditions stay data, never model calls (rule 2) |
| D-37 | 2026-10-15 | **Output fields are inferred by the assistant and shown as an editable list.** Inferred fields are proposals until the creator accepts them; a field used by a condition or lock keeps its id forever (renames change the label only). Resolves Q-10 | Creators don't think in schemas; stable ids keep conditions, locks and runs intact (rule 4) |
| D-38 | 2026-10-15 | **Review UI: local web app in v0.1, reachable on the LAN with a pairing token** so phone review works over home wifi; **PWA** (offline, push) with the hosted version in v0.4. Resolves Q-11 | Phone review without hosting or accounts; hosting brings the PWA |
| D-39 | 2026-10-16 | **Agent memory is an engine-owned context ladder:** decompose → offload (+`recall`) → clear → notes (`note`) → summarize → hand off; never a sliding window, no retrieval yet. Summarize at 70% of the context window down to ~30%, in batches; the agent may compact early. Structured digest with source hashes, checked by code (citations, carry-over). Node's own model by default (`compact_model` override, pinned). Protected: goal, locked inputs, lock notes, agent notes, human answers, last 6 turns. Planted-fact evals in CI. Resolves Q-16 | Replay stays exact; most bloat is removed with no model call and no loss; the one lossy step is checked; prompt caching survives |
| D-40 | 2026-10-20 | **SQLite through `better-sqlite3` with plain SQL**, no ORM, behind the `EventLog` / `BlobStore` interfaces. Schema changes are numbered migrations tracked in `user_version`. Tables are added when first needed. Local data lives in `.kriya/`. Supersedes Drizzle in 15-stack | The core is one append-only table plus projections; plain SQL is smaller and readable; interfaces keep the Postgres path open |
| D-41 | 2026-10-20 | **A map's output, as seen by later steps, is one list per child output in the order of the locked source list**, with `null` where an item produced nothing; `per_shot[P3-04].clip` reads one item. | D-42 | 2026-10-20 | **Who locks a step.** Screen buttons lock only when marked `locks: true` (no naming convention); they lock the selected version of the step the screen shows, or its only latest candidate. | D-43 | 2026-10-20 | **`result` in edge conditions** is the candidate the edge's source step just made; `<step>.<field>` always means locked output. | D-44 | 2026-10-21 | **`refines: <step>`** on a model, agent or tool step makes its output the next version of that step (parent = what the reviewing screen selected, else the locked or newest version; instruction = that screen's note). | D-45 | 2026-10-21 | **Stale tracking by per-input hashes.** Each version records one content hash per input (settings without labels, inputs or item, `uses` and prompt refs, preceding steps, a map's list and per-item outputs). | D-46 | 2026-10-21 | **Crash safety by atomic steps + idempotency keys.** The scheduler writes everything between two outside calls in one transaction, committed before each call. | D-47 | 2026-10-21 | **Context and assets.** Recipes declare `inherits: [series]`; the run records that context at start. | D-50 | 2026-10-23 | **The agent loop.** `Executors.turn(node, ctx, history)` makes one model call and returns tool calls (one or more, run in order) or a final output; the scheduler records `AgentTurn`, `ToolCalled`, `ToolResult` and loops. | D-52 | 2026-10-23 | **Agent file tools are a virtual workspace.** `write_file`, `read_file`, `list_files` are built-ins on a per-step, per-attempt workspace: the latest successful write per path, folded from history, contents stored by hash. | D-53 | 2026-10-23 | **Model calls are jobs; the engine stays synchronous.** Real providers are async; the engine is pure and synchronous. | D-54 | 2026-10-23 | **The Claude adapter.** `llm.write` / `llm.vision` steps: one request per candidate, answer constrained by structured outputs built from the step's `out` types (strict).
